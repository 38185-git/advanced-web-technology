# course-catalog-api

Course Catalog backend: FastAPI, SQLAlchemy, PostgreSQL, and Alembic migrations (Labs 4–7, Advanced Web Technologies).

## How to run

Requires Python 3.11+ and PostgreSQL 16+. Once, as the PostgreSQL administrator, create the role and database:

```sql
CREATE ROLE catalog_app LOGIN PASSWORD 'change-me';
CREATE DATABASE course_catalog OWNER catalog_app;
```

On this NixOS workspace PostgreSQL 17 is installed in the user Nix profile, with its persistent cluster in `~/.local/share/postgresql`. Start the local server with:

```sh
pg_ctl -D ~/.local/share/postgresql \
  -l ~/.local/share/postgresql/server.log \
  -o "-h 127.0.0.1 -k ~/.local/share/postgresql -p 5432" start
```

Stop it with `pg_ctl -D ~/.local/share/postgresql stop`.

From `course-catalog-api/`:

```sh
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
alembic upgrade head
psql -h localhost -U catalog_app -d course_catalog -v ON_ERROR_STOP=1 -f seed.sql
alembic check
fastapi dev main.py
```

Open http://localhost:8000/docs. The password in `.env.example` is for a local teaching database. Keep real credentials in `.env`; that file is ignored by git.

## What changed in the API

- Course, student, and enrollment data now lives in PostgreSQL and survives an API restart.
- `POST /students` creates a student. `POST /enrollments` now accepts `studentId` rather than a free-form `studentName` and returns the database enrollment id and timestamp.
- `GET /enrollments` includes the student and course names. New routes are `POST /students` and `GET /stats/courses`.
- Courses have a required `level` (`beginner` or `intermediate` for the initial rows); `GET /courses?level=beginner` filters by it. Elective courses receive `beginner` and other existing courses `intermediate` during migration 0002.
- Known constraint violations map by constraint name: duplicate email/enrollment → 409, missing course/student → 404. Pydantic rejects a too-short name with 422. Unrecognized integrity errors remain 500 so programming faults are visible.

## Database models and routes

`models.py` contains the SQLAlchemy tables; `schemas.py` describes JSON input and output. The constraint naming convention deliberately matches PostgreSQL's names. `POST /courses/{course_id}/like` uses one `UPDATE ... likes = likes + 1 ... RETURNING` statement to avoid lost updates. The enrollment listing uses joins, and course statistics use a left join with `count(Enrollment.id)` so empty courses show zero.

Useful local checks:

```sh
python check_db.py
python check_models.py
python try_errors.py  # start the API first; requires the seeded rows
```

`check_models.py` should show 6, 3, and 6 rows (after seeding) and `none` for both name mismatch lists. `try_errors.py` should report 5 of 5 expected responses.

## Bonus

### CHECK constraints and `op.f`

Alembic autogeneration and `alembic check` do not compare CHECK constraint definitions. The optional experiment adds `CheckConstraint("level IN ('beginner', 'intermediate', 'advanced')", name="level")`, observes a clean check and an empty autogenerated revision, then writes the change manually with `op.create_check_constraint(op.f("courses_level_check"), "courses", "level IN ('beginner', 'intermediate', 'advanced')")`. The matching downgrade is `op.drop_constraint(op.f("courses_level_check"), "courses", type_="check")`. `op.f` marks a name as final so the naming convention does not add `courses_` and `_check` a second time. The experiment migration and model constraint are deliberately removed afterward, as the assignment directs.

### Renaming a column without data loss

Alembic may interpret a model rename from `description` to `summary` as add-column plus drop-column, which loses the stored descriptions (and a required new column may fail on populated data). The correct experimental migration uses `op.alter_column("courses", "description", new_column_name="summary")`; downgrade reverses those names. This rename experiment belongs on the disposable `scratch` database and is removed after checking that the values remain under `summary`.

### N+1 queries

Run `python try_n_plus_1.py` with the API database seeded. With SQL logging enabled (`SQL_ECHO=true` in local `.env`), count repeated enrollment SELECTs while iterating courses: lazy loading performs one course query plus one query per course (7 queries for 6 courses). The script compares this with `selectinload`, which uses one course query and one shared enrollment query (2 total). `joinedload` fetches the collection in a single joined result set, repeating course columns for each enrollment and requiring row de-duplication; `selectinload` keeps the parent query separate and fetches children with an `IN` query.

### Lost update in the ORM

`python try_lost_update.py` demonstrates the naive read/increment/write pattern and then the database-side expression `a.likes = Course.likes + 1`. Two sessions can both read 11 and both write 12, losing one like. SQLAlchemy sends the expression as `UPDATE ... SET likes = likes + 1`; PostgreSQL locks the row during each update, so the second writer waits and increments the committed value to 13. The script restores the starting likes value when it finishes.

### ORM delete cascade

`Student.enrollments` keeps `passive_deletes=True`, matching the database's `ON DELETE CASCADE`. If it is removed for the experiment, SQLAlchemy loads the child enrollments and tries to set their required `student_id` to NULL before deleting the student, which fails NOT NULL. With `passive_deletes=True`, SQLAlchemy leaves child rows alone and PostgreSQL performs the cascade. `python try_delete.py` demonstrates the successful delete for student 3; reseed afterward to restore the six original enrollments.

## Migrations

| Command | What it does |
|---|---|
| `alembic upgrade head` | Applies missing migrations. |
| `alembic downgrade -1` | Rolls back the latest migration. |
| `alembic current` | Shows the database version. |
| `alembic history` | Shows the migration chain. |
| `alembic revision --autogenerate -m "text"` | Drafts schema changes from model/database differences; review the file before applying. |
| `alembic check` | Fails when model metadata and the database differ. |
| `alembic upgrade 0001:0002 --sql` | Prints migration SQL without running it. |
| `alembic stamp head` | Records a version without running migrations; use only when the existing schema is verified to match. |

Migration 0001 creates the Lab 6 tables, constraints, and student index. Migration 0002 adds `courses.level` in three steps: nullable column, backfill existing courses, then NOT NULL. Its downgrade drops the column and therefore removes level values. Review generated or hand-written migrations before applying them.

For a database that already has the Lab 6 schema and data, do not run migration 0001 against the existing tables. First verify it matches the models, then run `alembic stamp 0001` to record that baseline and `alembic upgrade head` to apply only migration 0002. The clean-start commands above are for a newly created empty database.

## Decisions

- Constraint names distinguish two different UNIQUE violations (email versus repeated enrollment); SQLSTATE 23505 alone cannot. Catching `IntegrityError` after `commit()` handles the race safely: a preflight SELECT can become stale before INSERT, while the database's unique constraint is authoritative.
- The like update is atomic in PostgreSQL. Reading a counter into Python and writing a derived value lets concurrent requests overwrite each other; `likes = likes + 1` lets the database serialize the row update.
- Migration 0002 adds the required value in three steps because existing rows need a value before NOT NULL can be enforced. The backfill rule is explicit and the downgrade is reversible at the schema level, though it discards level data.
